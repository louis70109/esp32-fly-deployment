# docs/ 規則：怎麼寫與維護 PRD

這個資料夾是專案的交接文件。**下一位（人或 Claude session）接手時只讀 `docs/` 就該能繼續工作**，
所以文件要比對話更可靠。寫 PRD 前先讀完這份。

## 檔案
- `PRD.md`：**唯一**的現行 PRD（活文件）。需求、現況、決策、待辦都在這裡。
- `PRD-TEMPLATE.md`：新專案或要重寫時的空白範本。
- 不要另開「PRD-v2.md」「新版PRD.md」。改 `PRD.md`，歷史交給 git。

## 規則

1. **一份文件、一個事實來源。** 更新現有 PRD，不要複製一份。改完同步改檔頭的「最後更新」日期與狀態，並在「變更紀錄」加一行。
2. **只寫程式碼讀不出來的東西。** 寫「為什麼」「限制」「待辦」「外部環境」。目錄結構、函式細節由程式碼和 README 負責，用檔案路徑指過去，不要重抄。
3. **區分「已驗證」和「未驗證」。** 每個「完成」的項目要寫怎麼驗證的（例如 `npm test` 18 項、線上端到端）。
   沒實測過的就明寫「未驗證」，不要寫成完成。草稿程式碼要標明是草稿。
4. **決策要寫理由與代價。** 格式：決定了什麼 → 為什麼 → 放棄了什麼 / 什麼情況下要重新考慮。
5. **待辦要有優先級與完成條件。**
   - `P0` 沒做就不能用 / `P1` 該做 / `P2` 使用者沒要求，**不要主動做**。
   - 每項至少寫一句「做到什麼算完成」。
6. **使用者的需求照原意記錄，不擴大。** 「需求」章節保留使用者的話（可整理）；你自己想到的點子只能放 P2，並標明是建議。
7. **絕不寫入機密。** 密碼、API key、token、`SESSION_SECRET` 都不能出現在 `docs/`、README、commit。只寫「存在哪裡」（例如 Fly secrets）與怎麼更換。
8. **用絕對日期**（2026-10-18），不要寫「昨天」「上週」。
9. **寫出環境怪癖。** 例如 Windows 指令差異、Node 版本、為什麼某個套件釘在舊版。這些是下一位最容易重踩的坑。
10. **語言：繁體中文**；指令、API、程式碼識別字保留原文。

## 交接前檢查（每個 session 結束時做）

- [ ] `PRD.md` 的「現況」反映真實的線上 / 程式狀態（部署了什麼、網址、region）
- [ ] 做完的待辦移到「現況」並註明驗證方式；沒做完的留在待辦
- [ ] 新發現的問題、警告、未驗證的假設都記下來（例如 Dependabot 警告）
- [ ] 檔頭日期與「變更紀錄」已更新
- [ ] `grep -riE "password|secret|key" docs/` 確認沒有真正的機密
- [ ] 已 commit（要不要 push 先問使用者）
- [ ] 如果下一位會在**另一台電腦**接手：必須已 push，且 PRD 有「從零開始」的步驟（clone、安裝、驗證指令、要先問使用者的問題）。沒 push 的工作對新電腦等於不存在

## PRD.md 的章節（順序固定）

1. 目標與使用者需求　2. 現況（已完成並已驗證）　3. 架構與決策　4. 介面摘要　5. 待辦（P0/P1/P2）　6. 開發與維運備忘　7. 變更紀錄

範本見 [PRD-TEMPLATE.md](PRD-TEMPLATE.md)。
